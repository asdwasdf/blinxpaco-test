# Paco Explore

## Mutation Mode
Ticket modes (`locate`, `observe`) read `manifest.yaml:mutationMode` before any side effect; default is `auto` whenever the host is in `paco.config.yaml: safety.allowedHosts` or `externalDevHosts`. `interact`, `autonomous` and `survey` have no ticket manifest and never read or write ticket `manifest.yaml`/`status.md`.

- `locate`: read-only (finding the route needs no side effect).
- `observe` with `mutationMode: auto`: **actively exercise the feature** — create/update/save/submit, delete/restore, upload/import/download on owned `QA-test` data without asking per action. Passive viewing alone is not a complete `observe`. Each mutation must pass `evaluateMutationGate()` and follow `docs/standards/data-safety.md` (`auto` mode).
- `observe` with `mutationMode: manual`/absent: read-only, record mutation candidates as unperformed actions.
- `interact` (no ticket, no discovery checkpoint): authorization is the tester-approved direct-exploration exception in `CLAUDE.md`, not a manifest. Same active exercise and hard limits as `observe` in `auto`. Before every mutation apply the same host check `evaluateMutationGate()` performs: environment in `safety.mutationEnabledEnvironments`, current URL HTTPS and hostname matching `allowedHosts`/`externalDevHosts`; otherwise stay read-only.
- `autonomous`: same authorization, host check and hard limits as `interact`, applied per feature inside the run; never uses discovery `--allow-mutation`/reservations.
- `survey`: the parent `paco-discover` reserves a mutation candidate and dispatches `paco-verify-flow`; this skill does not mutate inside a discovery task.

Hard limits in every mode: never modify/delete/send on pre-existing or shared data or real patient records; email only to the approved recipient, SMS needs explicit tester confirmation; irreversible, bulk, or externally visible actions outside owned test data need explicit authorization (ticket modes: `Mutation Policy: APPROVED` in `status.md`; `interact`/`autonomous`: explicit tester approval in the session for that action, recorded in the run ledger; `survey`: a `paco-verify-flow` reservation with tester-issued authorization); production/unknown host blocked. When the tester asks for observation only, stay read-only regardless of mode. If a `survey` task surfaces a candidate that this skill must hand back, the parent reserves the mutation, and `paco-verify-flow` runs it with the same safety rules as ticket `auto` mode: hostname allowlist, safe test data, approved recipient, production/unknown host blocked, ledger written, cleanup on pass/fail, leftover log on cleanup fail.

## Scope and dependencies

Require explicit mode `locate` (`LOCATE`), `observe` (`EXPLORE`), `interact` (`INTERACT`), `autonomous` (`AUTONOMOUS`) or `survey` (`SURVEY`), environment, valid auth in the current Claude Playwright plugin browser tab and role. `locate` and `observe` also require selected ticket and valid requirements; `interact` requires only a target feature/module (name, route or menu clue), `autonomous` requires nothing beyond auth/role (optional budget/focus) and `survey` only a discovery task. A request to explore/test a Paco feature without a ticket or discovery run is mode `interact`; a request to explore Paco (or `resume autonomous`) without naming one feature is mode `autonomous`. Read feature-location/product-survey/data-safety/evidence/knowledge standards and `scripts/manual-login.md`. Dùng Claude Playwright plugin-first.

**Auth pre-flight:**
1. Run `CHECK_AUTH_SCRIPT` from `scripts/paco-auth-helper.ts` via `browser_evaluate`. If `authenticated: true` → proceed.
2. If `authenticated: false`, call `buildFullLoginScript()` from `scripts/paco-auth-helper.ts` via `browser_evaluate`. Retry `CHECK_AUTH_SCRIPT`.
3. If still unauthenticated, return `Blocked: Authentication expired` and ask tester to run `npm run auth:login`. After tester reports completion, verify `authenticated: true` before resuming.
4. **NHS Comms Hub dev** (`nhs-comms-hub-dev.blinxhealthcare.com`, any mode that reaches it, e.g. a Paco handoff or an `autonomous` target): use `scripts/comms-hub-auth-helper.ts` instead — its `CHECK_AUTH_SCRIPT`, then `buildFullLoginScript()` (credentials from `.env`) if not authenticated, then `buildVerifyAuthScript()`. Run it only when the tab hostname is exactly that host. Still unauthenticated → `Blocked: Comms Hub authentication expired` for that target only; continue other targets on Paco.

Never request credentials or read, copy, persist, or report cookies, tokens, headers, or browser auth state. Không probe private APIs, infer intent, design suites hoặc orchestrate phases.

## Concurrent Execution Isolation

When running multiple tickets in parallel, ensure isolated browser resources:

1. **Check port allocation**: `npm run mcp:run:ports` before starting
2. **Create isolated run**: `npm run mcp:run:create <ticket-id>` for new tickets
3. **Cleanup**: `npm run mcp:run:cleanup <run-id>` after completion

Port conflicts cause MCP sessions to crash. Use unique ports 3200-3209 for concurrent runs.

## Browser connector

- The browser tools for every mode are the Claude Playwright plugin: `mcp__plugin_playwright_playwright__*` (server `plugin:playwright:playwright`). The project `.mcp.json` servers `playwright-user`/`playwright-plugin` are a different, optional pair; despite the name, `playwright-plugin` is **not** the Claude Playwright plugin.
- A session-start or mid-session notice that `playwright-user`/`playwright-plugin` failed (`CONNECTION_CLOSED`) is **not** a browser loss and never a blocker. Note it once in the ledger, then continue. Real connector loss = a `mcp__plugin_playwright_playwright__*` call itself errors with a transport/closed-page error (tool timeouts like `locator.click: Timeout` are product/locator issues, not connector loss).
- Before concluding connector loss, make one cheap probe (`browser_tabs` list or `browser_snapshot`). Only if the probe also fails is the browser `Blocked`.
- Recovery (manual, not automatic): state is already persisted (see `Mode autonomous` checkpoint rule) → probe again; if the plugin tool still fails, ask the tester to run `/mcp` and reconnect `plugin:playwright:playwright` (or restart Claude Code). After reconnect: auth pre-flight, verify role from UI, reconcile pending ledger lines (read-only search of the `QA-test` name), then continue from `next_steps`. Never retry a mutation whose result is unknown before reconciling it; never re-do features already `done` in the checkpoint.
- Known root cause (2026-10-22): `.mcp.json` servers started with `--port` left orphaned HTTP listeners on 3101/3102, so later sessions failed with `EADDRINUSE` → `CONNECTION_CLOSED`. `--port` is removed; if it recurs, check `ss -ltnp | grep 310` and the logs in `~/.cache/claude-cli-nodejs/<project>/mcp-logs-*`.

## Ownership

Mode `locate` writes `feature-location.md` plus its feature entry route fields in `docs/product/feature-map.md`; mode `observe` writes `exploration.md` plus the ticket knowledge sync (`docs/product/feature-map.md` entry + `Ticket → feature` row, `docs/product/workflows/<module>.md` section `## Logic từ ticket`, `docs/product/open-questions.md`, `docs/product/change-log.md`); mode `interact` writes `docs/product/workflows/<feature>.md` (template `docs/templates/workflow.md`), its `docs/product/feature-map.md` entry, `docs/product/open-questions.md`, a dated `docs/product/change-log.md` line, and the run ledger/evidence under `test-results/product-explore/<run-id>/` (never ticket files, manifest/status or discovery checkpoint); mode `autonomous` writes everything `interact` writes for each feature it explores, plus `docs/product/explore/autonomous-state.yaml` (template `docs/templates/autonomous-explore-state.yaml`; the only autonomous resume checkpoint) and `docs/product/explore/relationships.md`, with run ledger/evidence/outcome under `test-results/product-explore/<run-id>/` (never ticket files, `docs/product/survey/**` or discovery checkpoints); mode `survey` writes `docs/product/paco-overview.md`, selected `docs/product/workflows/<feature>.md` files using `docs/templates/workflow.md` and `docs/product/survey/views/*.md`; mode `observe` may also append to `docs/tickets/<ticket>/test-data-ledger.md` (redacted mutation ledger); never discovery checkpoint, manifest/status or `ticket/**`. Preserve final `## Tester notes` in every managed file. Raw locate evidence stays under `test-results/<ticket-key>/locate/<run-id>/`; raw survey evidence stays under `test-results/product-survey/<run-id>/`; only reviewed/redacted evidence enters docs.

## Mode `locate`

1. Require `environment`, `role`, auth and read-only mode. Ask optional module/page/context/menu clues; “không biết” is not blocker and tester clues remain tester-provided.
2. Read exact terms, aliases, actor/context and trigger/target nouns from requirements. Check `feature-map.md`, then matching files under `docs/product/workflows/`; treat survey workflow routes/context only as search hints and validate a reusable route in 1–3 meaningful views.
3. If hinted route is missing/stale/mismatched, scan from dashboard through global navigation, page search, visible menu, authorized contextual menu and read-only detail. Stop at verified route, 12 meaningful views or 15 minutes.
4. Count only new useful page/module/menu/dialog/drawer/search-result states. Retry, reload and same-state screenshot do not count.
5. Allow navigate/view/search/filter/sort/paginate and known read-only detail/menu/dialog. Stop before mutation, send/upload/import, adding an item to a draft/template or unknown persistence.
6. Record ordered entry path, context, landmarks, up to three useful candidates, rejected paths with dependency revision, budget and exact next action. Do not assert business behavior.
7. Keep browser output compact: full `browser_snapshot` once per new state; do not re-snapshot an unchanged known state; `browser_evaluate`/`browser_run_code` return only the values needed (labels, counts, status, error text), never full DOM/HTML. Exploration may still snapshot fully whenever a state is new or unexpected, so unknown behavior is not missed.
8. Capture only useful milestones: module/context landmark, entry control/menu and opened feature root. Never put unredacted PII/auth data in docs.
9. **Route sync:** once route status is `Confirmed`, add/update the feature entry in `docs/product/feature-map.md` (ordered `Entry`, `Route`, role, environment, `Classification: Observed`, `Last verified`, source `PAC2-xxxx/feature-location.md`) using allowlisted fields only. Unverified candidates go to `Route hints (chưa verified)`. Return synced file + checksum in outcome.

## Mode `observe`

1. Start only from valid feature location or documented non-UI exception; use matching product workflow only as context and re-verify current state.
2. Record environment, role, scope and timestamp.
3. Map the feature's interactions first (one snapshot per new state): entry points, forms, required fields, actions, statuses. Then, in `auto` mode, exercise the workflows in scope with owned `QA-test` data, prioritizing what the requirements touch:
   - **Create/submit:** happy path with minimal valid data; record resulting state, toast/message, list/detail appearance.
   - **Validation:** empty required fields, invalid format/boundary values, duplicate name; record exact messages and whether submit is blocked.
   - **Update / state transitions:** edit own record, change status/toggle, cancel vs save, decision branches visible in UI.
   - **Persistence:** reload or re-open after each mutation and verify the data/state really persisted (and in related views when the ticket implies a handoff).
   - **Delete/restore/upload/import/download** when part of the feature; use synthetic files only.
   Before each mutation write a ledger line (action, object `QA-test-…`, class, expected cleanup); after it record result. Stop and ask only at the hard limits in `Mutation Mode`, a missing domain rule/safe test data, or an action whose target is not owned test data. Unknown persistence on owned data is something to exercise and verify, not a reason to stop.
   Efficiency: batch deterministic multi-step sequences into one `browser_run_code` returning only needed values; snapshot only new/unexpected states. Never skip a meaningful interaction just to save calls.
4. Cleanup all `QA-test` records created (via UI delete or reverse action), verify cleanup, log leftovers in ledger and outcome. Separate `Observed` behavior from intent; record still-unperformed actions with reason, mismatch, possible defect and suggested coverage.
5. **Ticket knowledge sync (mandatory before `MANUAL_EXECUTE`, also when `EXPLORE` ends `Blocked`/`Inconclusive`):** merge requirements-derived logic (keep `Confirmed`/`Inferred` from `requirements.md`), the discovered workflow (ordered steps, forms/fields, validation messages, states/transitions, persistence) and interaction-verified behavior (tag `Observed`, provenance includes ledger entry; still never `Confirmed`) into `docs/product/workflows/<module>.md` under `## Logic từ ticket` (flow steps, business rules, states, role/permission, possible defects, open questions; every bullet keeps classification tag + `PAC2-xxxx/<file>` provenance; create the module file and index it in `workflows/README.md` if none fits). In `docs/product/feature-map.md` update `Logic chính` (2–4 rules), `Chi tiết:` link and the `Ticket → feature` row (status = current phase). Append unresolved questions to `open-questions.md` and a dated `change-log.md` line. Dedupe; on conflict keep both with provenance; never upgrade to `Confirmed`; no PII/test data/fragile locators; preserve `## Tester notes`. Unsafe merge is a blocker, never a silent skip. List synced files + checksums in the outcome.

## Mode `interact`

Independent product exploration; never part of ticket testing and never updates a discovery checkpoint. `run_id` = `explore-<feature-slug>-<YYYYMMDD-HHmm>`.

1. **Locate:** reuse `feature-map.md`/`workflows/<feature>.md` route; otherwise navigate from dashboard (same read-only rules and budget as `locate` steps 3–4). Record entry path and landmarks.
2. **Map interactions:** one snapshot per new state; list forms, fields (required/format), actions, statuses, tabs, dialogs and handoffs. Classify each action `CREATE`/`UPDATE`/`DELETE`/`SEND`/`UPLOAD`/`DOWNLOAD`/`EXTERNAL_SIDE_EFFECT`/read-only, and mark whether the feature supports it. Do not force CRUD the feature does not offer.
3. **Plan data:** synthetic `QA-test-<run-id>-<n>` names, no real PII, synthetic files only. If a required field needs a domain value or pre-existing record you cannot create, Ask QA early and continue other branches.
4. **Exercise each supported workflow** on owned data, in this order: create/submit → validation (empty required, invalid format/boundary, duplicate; record exact message and whether submit is blocked) → read back in list/detail → update/edit (save vs cancel) → state transitions/toggles and decision branches → **persistence** (reload or re-open; verify value/state) → cross-feature handoff (check the related view the UI points to) → upload/download when offered → delete/restore last (only own records). Before each mutation re-check host allowlist and append a redacted ledger line to `test-results/product-explore/<run-id>/ledger.md` (action, class, object, expected cleanup); after it record result/evidence.
5. **Stop-and-ask only for:** pre-existing/shared data or real patient records as target; `SEND` to anyone other than the approved email recipient; any SMS; bulk/irreversible actions or external systems outside `externalDevHosts`; unclear target ownership. Record these as skipped with reason and continue.
6. **Cleanup:** remove/revert every owned record via UI, verify by reload/search, record leftovers.
7. **Efficiency:** batch deterministic steps in one `browser_run_code` returning only needed values; long or repeated scripts go to a file under `test-results/product-explore/<run-id>/`. Snapshot new/unexpected states fully. Never drop a meaningful interaction to save calls.
8. **Knowledge sync:** update `workflows/<feature>.md` using the template sections (location, business workflow, required test data, interactive flow, validation, state/persistence, cross-feature relationships, anomalies, unverified behavior/blockers, mutation coverage). Interaction results are `Observed` with provenance `product-explore/<run-id>/ledger.md#<n>`; never `Confirmed`, never ticket requirements/expected results. Dedupe, keep conflicts with provenance, preserve `## Tester notes`. `Coverage` may be `Complete` only when every supported action in step 2 was exercised; read-only only ⇒ `Partial (read-only)`.

## Mode `autonomous`

Self-directed whole-app exploration: one invocation, no ticket/feature/route input. Runs the `interact` procedure per feature, chosen by the agent. Never part of ticket testing; never reads/writes `docs/product/survey/roles/*.discovery.yaml` or calls `npm run paco:discover`. `run_id` = `auto-<YYYYMMDD-HHmm>`.

**State file** `docs/product/explore/autonomous-state.yaml` (create from template if missing; one `roles.<role>` block per role). It holds: app map (module → features, entry, status `unmapped|mapped|partial-interactive|deep|blocked`, coverage dimensions, last_verified), frontier queue (target, reason, provenance, priority), open questions, active/last run (run_id, budget used, current target, stage), leftovers (owned records not cleaned) and `next_steps`. Redacted only: no PII, no auth data, no QA record ids beyond the `QA-test-<run-id>-<n>` name. Write it after every finished feature and before any `/clear` prompt — it is the resume source, not the conversation.

**Budget** (defaults; tester may override): `max_features: 6`, `max_minutes: 120`, `max_meaningful_states: 80`. Per feature soft cap 25 meaningful states; exceeding it records remaining branches in the frontier instead of stopping silently. Reaching budget is a checkpoint, never a coverage claim.

1. **Start/resume:** auth pre-flight; verify role from UI. Read state file, `feature-map.md`, `workflows/README.md`, `explore/relationships.md`, `open-questions.md`. If state has an active run with `stage` ≠ `done`: verify the current tab (URL/landmark) matches `current_target`; first reconcile `leftovers` and any ledger line without result by read-only check (search the `QA-test` name) — clean up if present, record `indeterminate` if unclear, never blindly redo. Then continue from `next_steps`; start from Dashboard only when the map is empty or the target route is unknown/stale.
2. **Map the app (first run, or stale map >14 days):** from `/paco/dashboard`, enumerate sidebar/top-nav/submenus/settings/user menu in one compact `browser_evaluate` (labels + hrefs only); merge with `feature-map.md`. Every module/feature gets a state entry; existing knowledge is reused but marked `needs-reverify` when older than 14 days or contradicting what is visible. Do not open every page — mapping is labels, routes and one landmark per module.
3. **Prioritize by business value, breadth first** (re-score after each feature).
   - **Module tiers** (starting priorities, not hardcoded routes; a module may be absent for the role): T1 Patient / Patient Search / Patient Profile; T2 Appointments / Appointment Book; T3 Communications / Comms Hub / Web Chat & Video; T4 Documents / Health Forms; T5 Role Groups / permissions; T6 other operational modules (Case Load, Capacity & Demand, Analytics & Reports, PACO Assist…); T7 Configuration / Organisation administration and other settings.
   - **Breadth gate:** while any T1–T5 module has no feature beyond `unmapped`, the next target must come from the highest such tier, unless an observed dependency/handoff edge from this run points elsewhere. Breadth pass per module = locate root, map main entities/actions, run the main workflow once on owned data where safe; deep branch coverage comes after every T1–T5 module has had a breadth pass.
   - **Same-area limit:** at most 2 consecutive features from the same module/submenu (e.g. `Configuration > Organisation`) while a higher-tier module is still `unmapped`.
   - Within a tier score high → low: (a) relationship/handoff targets observed in this run, (b) `unmapped`/no workflow doc, (c) `partial (read-only)` with visible CRUD/submit not covered by a pending decision, (d) features others depend on (patient context, documents, templates), (e) open questions answerable by interaction, (f) `needs-reverify`.
   - Skip `blocked` features and any branch linked to a `pending` decision (see step 9) unless the blocker/decision changed; skip `deep` unless re-verify is due. Record why the target won in one line in the run ledger. Never pick by random click or navigation order.
4. **Per feature — hypothesis loop** (inside `interact` steps 1–7, same safety and ledger):
   1. Write a hypothesis: purpose, actor, entities, expected main flow, what other module it feeds/consumes — labelled `Unverified hypothesis`.
   2. Choose the smallest interaction that tests it (often: create minimal owned record → see where it appears).
   3. Execute, observe end state (UI, then persistence by reload/re-open).
   4. Compare: confirmed-by-observation → `Observed`; contradicted → keep both, note it; unexpected → focused investigation (repeat on fresh page, vary one input, then console/network once — see Technical investigation) before calling it `Possible defect`.
   5. Record new questions/branches in the frontier; pick the next experiment. Stop the feature when main flow + supported branches are exercised or the soft cap is hit.
   6. **Depth check** after the main workflow: continue deeper only if the next branch is likely to verify a mutation/persistence, a cross-feature relationship or answer an important open question; otherwise push the remaining branches to the frontier and move on (breadth gate in step 3 wins over polishing a low-tier feature).
   Cover: purpose, access/role, prerequisites, entry points, entities, forms/fields/validation, happy path, alternative branches, state transitions, empty/loading/error/success states, persistence, negative/edge cases. Missing data is not a stop: create the prerequisite owned `QA-test` record in its source feature (add that feature to the frontier as a dependency edge) when it is creatable within the safety rules.
5. **Relationships (high priority):** for each record you create, ask where else it could appear (lists, pickers, patient context, reports, comms, templates) and check the 1–3 most plausible views; follow a handoff link the UI exposes. A relationship is recorded only with observed evidence on both sides (`from` action → `to` observed effect); name similarity alone is `Inferred` at most. Also check what happens downstream when the source record is edited/deleted, when that is safe on owned data. Append to `docs/product/explore/relationships.md` (`From → To | Trigger | Observed effect | Classification | Evidence/ledger ref | Last verified`) and to both features' `## Cross-feature relationships`. Enqueue the `to` feature if under-explored.
6. **Technical investigation (selective):** only for silent failure, unclear mutation result, persistence mismatch or a confusing handoff: `browser_console_messages` (errors only) and `browser_network_requests` summarized to method + path pattern (ids replaced by `:id`) + status. Never record bodies, headers, cookies, tokens, query values or PII; never replay/fuzz/call endpoints. HTTP 2xx is supporting evidence only — persistence is proven by UI after reload/re-open.
7. **After each feature:** cleanup (as `interact` step 6), knowledge sync (as `interact` step 8 — dedupe, conflicts kept with provenance, `## Tester notes` preserved, re-verified facts update `Last verified`, stale facts that no longer reproduce are marked `Not reproduced <date>` not deleted), update coverage dimensions in state, write state file.
8. **Coverage dimensions** per feature (each `none|partial|done|n/a` + note): `navigation`, `main_workflow`, `branches_states`, `mutation`, `validation`, `persistence`, `relationships`, `errors_edge`. Status `deep` only when no dimension is `none`/`partial` without a recorded reason (`n/a`, blocker); otherwise `partial-interactive`. App-level coverage = counts per status + list of `unmapped`; never claim the app is covered because navigation produced no new items.
9. **Shared decisions (grouped blockers):** classify every mutation before running it as `owned-row` (only affects an owned `QA-test` record, cleanup proven in UI), `whole-list` (page-level/footer `Save` that submits a shared list or shared configuration) or `unknown-scope`. `owned-row` follows normal rules. `whole-list` and `unknown-scope` are never executed without tester authorization: link the feature to an existing entry in state `decisions` with the same root cause (e.g. `DEC-shared-list-save`), or create one decision with one OQ — never a new OQ per feature for the same cause. Continue the feature's independent read-only/owned branches, then move on. A branch linked to a `pending` decision is not retried, not re-reconciled and not re-described each run; it reopens only when the tester answers the decision (recorded in state `decisions[].answer` and the ledger). When a run ends with pending decisions, the report ends with one consolidated question per decision listing all affected features.
10. **Writing rules (state, docs, OQs):** `coverage_note` and `blocker` ≤ 2 short sentences in plain prose; no millisecond/clock timestamps (dates only, `YYYY-MM-DD`); no compressed tokens such as `rows0/dialogs0/roletrue` — write `0 rows, 0 dialogs`; no repeated generic disclaimers ("không product verdict", "không deep", "không claim…") — classification tags already carry that; refer to evidence by ledger ref only. Chronological actions, timestamps, counts and diagnostics live in the run ledger only. State keeps current progress and next actions, not history: `runs` holds one line per run, `next_steps` ≤ 5 items each ≤ 1 sentence, cleanup history lives in the ledger (state keeps only `leftovers` and `retained_records`). Workflow docs hold reusable behavior; OQs hold the question, impact (1 sentence), evidence refs and linked features.
11. **Progress metric** (end-of-run report and `runs[]` line): count new business workflows investigated (T1–T6), branches with observed end state, mutations with verified persistence, two-sided relationships, decisions/blockers unlocked, and important OQs closed. Page views, tool calls and document length are not progress.
12. **Checkpoint before risky transitions:** write the state file (stage, current target, pending ledger line) before every mutation batch, before leaving a feature, and before any long-running script, so a connector loss resumes from the last safe point without replaying completed work.
13. **End of run** (budget hit, frontier empty, or blocker): final cleanup sweep for this run's ledger, write state (`stage: done` or `paused`, concrete `next_steps`), write `outcome.json`, print the report (see Outcome), then per CLAUDE.md context budget: recap ≤10 lines ending `Gõ /clear rồi nhập: resume autonomous paco-explore`. Long sessions also checkpoint+prompt `/clear` between features, never mid-feature.

## Mode `survey`

1. Require `environment`, role, auth và đúng một task do `paco-discover` giao (`run_id`, `task_id`, checkpoint `revision`). Ticket/requirements không bound discovery. Crawl current role only; role switch is manual và uses separate checkpoint. Gọi trực tiếp không có task thì chỉ quan sát read-only và trả proposal; không bắt đầu vòng lặp, không sửa checkpoint.
2. Quan sát task được giao rồi các state lân cận trong budget nhỏ. Mô tả state bằng `DiscoveryStateDescriptor`: role, URL, heading/module, tab, dialog/drawer, entity/context type và data-state variant; khai báo `meaningful_query`/`volatile_segments` chỉ khi đã quan sát chúng đổi workflow. Query/segment không phân loại được thì ghi gap, không đoán. Planner/checkpoint thuộc parent; đạt ceiling không kết luận coverage đủ.
3. For each selected feature record visible business purpose, actor/role, required context, starting data state, entities/statuses, ordered read-only actions, state transitions, decision branches, end/error/empty/loading states, cross-feature handoffs and exact mutation boundary. Do not infer intent from labels alone.
4. Count only a new state that adds workflow knowledge: page/module/menu/dialog/drawer/search-result, a changed filter/sort/page state, or a read-only detail transition. Retry, reload and same-state screenshot do not count.
5. `survey` strictly read-only: không mutation, upload, import, send hoặc action chưa rõ persistence. Gặp action như vậy thì dừng trước nó và **luôn** trả structured mutation candidate (không chỉ ghi gap) cho mỗi CREATE/UPDATE/DELETE/SEND/upload có workflow phía sau, kèm candidate cleanup tương ứng (`cleanup_of`) và `persistence` đã phân loại (`Unknown` sẽ bị gate chặn — chỉ dùng khi thật sự không thể phân loại); trả mutation candidate (class `CREATE`/`UPDATE`/`SEND`/`DELETE`/`EXTERNAL_SIDE_EFFECT`, persistence, lý do cần thiết, evidence, required test data/recipient, `destination_hint` chỉ là giả thuyết). Relationship tại boundary có `mutation_boundary: true` và không có `to`. Mỗi candidate phải đi kèm một `new_tasks` entry `category: mutation`, `provenance: { kind: 'candidate', ref: <candidate.id> }`, `candidate.task_id` = id của task đó và `source_state` = fingerprint của state đã có trong `observed_states`; thiếu thì `apply` từ chối cả outcome. ## Outcome

**Mutation coverage report (mandatory for `observe`, `interact` and each feature of `autonomous`, in outcome and in the workflow doc `## Mutation coverage`):** evaluate per workflow branch, not per CRUD action. For each meaningful branch found in the interaction map (e.g. create→list, edit→save vs cancel, status A→B, role/condition branch, cross-feature handoff, upload/download) report: exercised (`Performed`/`Skipped` + reason/`Not supported`), validation rules tried vs found, state transitions observed vs visible, persistence verified (reload/re-open/related view, or no), cleanup (`Done`/`Leftover`/`N/A`). Then summarize `branches exercised / branches found` and list branches, validations and transitions still untested. A branch counts as exercised only when its end state was observed; read-only observation alone is reported as `Partial (read-only)`, never fully explored.

`LOCATE`/`OBSERVE` return `ChildSkillOutcome` v1; `LOCATE` also returns location mode, route status, budget and next action with mutation `None`; `OBSERVE` also returns mutations performed (ledger refs), cleanup status and leftovers. `INTERACT` returns a plain JSON summary (not `ChildSkillOutcome`, which is ticket-bound; not `DiscoveryChildOutcome`) with mode `INTERACT`, run_id, synced files + SHA-256, mutation coverage report, ledger path and blockers; written to `test-results/product-explore/<run-id>/outcome.json`. `AUTONOMOUS` returns the same plain JSON shape per feature inside one run summary in `test-results/product-explore/<run-id>/outcome.json` and prints a report with: (1) modules/features discovered, (2) workflows investigated, (3) important business behavior observed, (4) mutations executed, (5) validation and persistence verified, (6) relationships, (7) possible defects/unexpected behavior, (8) remaining gaps/frontier, (9) cleanup status and leftovers, (10) updated knowledge files, (11) coverage by dimension and limitations, (12) exact resume instruction — each item tagged `Observed`/`Inferred`/`Unverified hypothesis`/`Open Question`. `SURVEY` returns `DiscoveryChildOutcome` (`scripts/discovery-outcome.ts`) với `mode: SURVEY`, `mutation: null`, observed states, evidence refs, relationships, new grounded tasks (provenance trỏ evidence/edge/gap/candidate), mutation candidates, gaps, artifacts kèm SHA-256 và blockers; ghi JSON vào `test-results/product-survey/<run-id>/outcomes/`. Auth hết hạn: `auth_expired: true`.
